## Repository purpose

This is a GitHub profile README repository (repo name matches the GitHub username `IKQR`), rendered on the owner's GitHub profile page. The profile content itself is not a software project — no build system, linter, or tests for the Markdown files. The repo also contains one small Python utility, `resume/`, that renders the profile Markdown into a PDF résumé (see below); that subdirectory has its own dependencies (`resume/requirements.txt`) but no build/lint/test tooling either.

## Files

- `README.md` — the profile page itself (rendered on github.com/IKQR). Links out to `SKILLS.md`, `EXPERIENCE.md`, `PROJECTS.md`, `LANGUAGES.md`, `CERTIFICATES.md`, and `EDUCATION.md`.
- `Summary.md` — a single professional-summary paragraph under a `# Summary` heading, used as the opening paragraph of the generated PDF résumé (see `resume/`).
- `SKILLS.md` — categorized list of programming languages, frameworks, technologies, clouds, databases, infrastructure, and tools.
- `LANGUAGES.md` — spoken/written language proficiency, one bullet per language as `Language — Proficiency level`.
- `CERTIFICATES.md` — licenses and certifications, formatted per certificate as `Certificate` / `Skills`, with issuer sections separated by `---` and a `> <date range>` line under each issuer heading (sourced from LinkedIn's Licenses & Certifications section).
- `EXPERIENCE.md` — reverse-chronological commercial work history, formatted per role as `Project` / `Description` / `Responsibilities` / `Contribution` / `Technologies`, with company sections separated by `---` and a `> <date range>` line under each company heading.
- `PROJECTS.md` — pet projects, side projects, and charity/volunteer work not tied to an employer (indie games, personal/university projects), using the same per-project block format as `EXPERIENCE.md` but as a flat list (no company/studio grouping headings, no date line); the studio or initiative name, if any, goes in the `**Project**:` line itself (e.g. `Name — Studio`).
- `EDUCATION.md` — education background, formatted per degree as `Degree` / `Faculty`, with institution sections separated by `---` and a `> <date range>` line under each institution heading.
- `resume/` — Python script (`scripts/generate_resume.py`, ReportLab-based) that parses `Summary.md`/`SKILLS.md`/`EXPERIENCE.md`/`PROJECTS.md`/`EDUCATION.md`/`CERTIFICATES.md`/`LANGUAGES.md` using the structured conventions below and renders them into a PDF résumé under `resume/output/`. All header fields (name, location, email, phone, LinkedIn, GitHub, Spotify) are read from environment variables with defaults in `resume/scripts/config.py`; the private ones (phone, location) default to empty rather than being committed. See `resume/README.md` for usage.
- `.github/workflows/release-cv.yml` — CI pipeline that regenerates the PDF résumé on changes to the files above (or a manual trigger) and publishes it as a dated GitHub release + tag (`cv-<year>-<month>`); see `resume/README.md`'s "CI: automated releases" section.
- `LICENSE` — MIT license.

## Editing conventions

- `EXPERIENCE.md`: one `## Company Name` heading per employer, followed by a `> Month Year - Month Year` (or `- present`) date line, then one project block per project. Each project block starts with `**Project**: Name` (link the name with `[Name](url)` when a URL exists), followed by `**Description**:`, optionally `**Responsibilities**:` (omit if unknown — don't invent it), optionally `**Contribution**:` (a concrete, standout statement of the developer's effect on the project — use it sparingly, only for genuinely impressive results, written as prose in the same style as `**Responsibilities**:` unless the content naturally calls for a bullet list, as in older entries; the biggest headline-level claims belong at the top of the résumé rather than repeated on every project), and `**Technologies**:` (list `.NET <version>` and `ASP.NET` as separate entries rather than combined), in that order. A single `---` separates every project block, including the last project of a company from the next company's heading. Newest roles are added at the top; do not reorder existing history.
- `PROJECTS.md`: same per-project block format as `EXPERIENCE.md` (`Project` / `Description` / `Responsibilities` / `Contribution` / `Technologies`), but as a flat list of project blocks separated by `---` — no company/studio grouping headings and no date line.
- `EDUCATION.md`: one `## Institution Name` heading per school, optionally followed by a `> Month Year - Month Year` (or `- present`) date line shared by every degree at that institution, then one degree block per degree, in the same order as `EXPERIENCE.md`'s project blocks. Each degree block has `**Degree**:` (degree level and field), `**Faculty**:`, and optionally `**Dates**:` (`Month Year - Month Year`/`- present`) when that specific degree's period differs from the institution's shared line above — e.g. a bachelor's finished before a later, separately-dated master's at the same school (omit the institution-level `>` line entirely when every degree there needs its own `**Dates**:`). A single `---` separates every degree block, including the last degree of an institution from the next institution's heading. Newest degrees are added at the top.
- `SKILLS.md`: organized under `#` category headings (Frameworks, Technologies, Architecture & Practices, Programming languages, Markup languages, Clouds, Databases, Infrastructure, Tools, Leadership & Process, AI Tools, Operating systems). Bullets use a single `- ` with 2-space indent per nesting level. Primary/strongest skills in a category are bolded (e.g. `**C#**`, `**PostgreSQL**`).
- `LANGUAGES.md`: a flat, unheaded bullet list, one line per spoken/written language as `- Language — Proficiency level`.
- `CERTIFICATES.md`: one `## Issuer Name` heading per organization, followed by a `> Month Year - Month Year` date line spanning that issuer's certificates, then one certificate block per certificate. Each block has `**Certificate**: Name` (link the name with `[Name](url)` when a verification URL exists) and optionally `**Skills**:`, in that order. A single `---` separates every certificate block, including the last certificate of an issuer from the next issuer's heading. Newest issuers are added at the top.
- `README.md`: one fact per line as `<code>&lt;emoji&gt; Label: value</code>`, blank line between entries, no trailing whitespace or stray HTML inside the `<code>` span.
- `Summary.md`: a `# Summary` heading followed by one plain-prose paragraph (no bullets) - the professional-summary blurb shown at the top of the generated résumé.

There are no commands to build, lint, or test the profile Markdown files - changes are plain Markdown edits. `resume/scripts/generate_resume.py` is the implemented PDF-résumé generator described above; the structured headings/labels in the conventions above exist specifically to keep it parseable, so keep following them when editing any of the source `.md` files.

## Opening pull requests - always pass `--repo`

This repo has two remotes: `origin` (`IKQR/IKQR`, this repo, the one to actually work against) and `upstream` (`HowProgrammingWorks/Profile`, the unrelated public template this repo was originally generated from - not owned by this account, never the intended target). Because `upstream` looks like a fork parent, `gh pr create` with no `--repo` flag silently opens the PR against `HowProgrammingWorks/Profile` instead of `IKQR/IKQR`, which has actually happened before (see the closed cross-repo PR in `IKQR/IKQR#2`'s history). Always create PRs with an explicit target, e.g. `gh pr create --repo IKQR/IKQR ...`, and double-check the returned URL starts with `github.com/IKQR/IKQR` before treating the PR as done.
